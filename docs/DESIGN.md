# 设计说明：多中转站聚合

在现有桌面应用基础上，支持用户绑定多个中转站账号（new-api / sub2api），把所有站点的分组放在一起切换。
体验与现在一致：选分组 → 自动写入 Claude Code / Claude Desktop / Codex / Gemini CLI。

## 已定的决定

- **不设默认站点**。首次启动是空状态，引导用户添加站点。
- **sub2api**：邮箱 + 密码登录（现有实现）。
- **new-api**：账号密码登录（与 sub2api 体验一致）。开启了人机验证、2FA 或关闭密码登录的站点暂不支持。系统访问令牌方式评估过但未采用。

## 已核实的 new-api 事实（v1.0.0-rc.45）

- `GET /api/status`（无需登录）返回 `version`、`quota_per_unit`（500000）、`display_in_currency`、
  `quota_display_type`、`top_up_link`、`usd_exchange_rate`。可用来**识别站点类型**和**换算余额**。
- 登录 `POST /api/user/login` 返回约 15 分钟有效的 Bearer 访问令牌，同时下发刷新 Cookie `new_api_refresh`；续期用 `POST /api/user/auth/refresh`。接口调用带 `Authorization: Bearer` 与 `New-Api-User: <用户 id>`。
- 管理接口：`/api/user/self`（余额）、`/api/user/self/groups`（可用分组）、`/api/token/`（GET 列表 / POST 创建，带 `group`）、
  `/api/token/:id/key`（POST，取令牌**明文**，列表里的 Key 是脱敏的）。
- **rc.45 引入了带权限范围（scopes）的访问令牌**：`/api/user/access_tokens`，只在创建时显示一次明文，库里只存哈希；
  同时保留旧的整体访问令牌（`/api/user/access_tokens/legacy`）。含 `group:read`、`user:read`、`billing:read`、`log:read` 等范围。
  **建 Key 需要哪个范围我还没验证**，要用真实令牌测（见下）。
- 老版本的 new-api 只有旧式令牌；站点版本不同，接口可能有差异，必须做“失败即降级、给清楚提示”。

## 架构

### 适配器接口（每种系统一份实现）

```
SiteAdapter:
  detect(base_url)            识别类型与版本
  verify(credential)          校验凭据，返回账号信息（邮箱/用户名、余额）
  groups()                    可用分组：id、名称、平台（anthropic/openai/gemini…）、倍率
  ensure_key(group)           找到或创建该分组的专用 Key，返回明文
  models(key)                 该 Key 能用的模型
  balance()                   余额，统一换算成显示用的金额
  topup_url()                 充值页地址
```

- `Sub2apiAdapter`：沿用现有 `api.rs`。
- `NewApiAdapter`：新增。分组的“平台”在 new-api 里没有字段，需要由模型列表推断（含 claude → anthropic，gpt → openai，gemini → gemini）。

### 数据模型

```
Site     { id, kind(sub2api|newapi), name, base_url }
Account  { site_id, 凭据（sessions.json）, 显示名 }
GroupRef { site_id, group_id }      // 分组的唯一标识
Active   { client → (site_id, group_id, model) }
```

- 同名分组在不同站点并存，界面一律带站点标签。
- 凭据只存在应用数据目录的 `sessions.json`（0600）：sub2api 存 refresh token；new-api 存轮换的刷新 Cookie（每次刷新都会换新，必须保存）。**不存密码**。
  不用钥匙串的原因见 SECURITY.md：ad-hoc 签名每次更新标识都会变，钥匙串会反复弹授权框。
- 站点列表和使用状态存本机应用数据目录；Key 命名 `Ferrydeck-<分组名>`（旧版的 `desktop-<分组名>` 仍识别复用），按站点各自创建。

### 写入层

每个客户端同一时刻只指向一个（站点，分组），所以写入层与站点无关：切换站点就是覆盖同一组固定的配置项。

- Codex：固定使用 `[model_providers.ferrydeck]` 这一个 provider。
- Claude Desktop：固定使用一个方案 id，在 `_meta.json` 里登记并设为当前。
- “用户原始配置”**全局只记录一份**：第一次写入前记录，之后无论切到哪个站点，都不会把我们写过的内容当成“原始”。
- 每个站点的使用状态（哪个客户端正在用哪个站点的哪个分组）单独记在 `active.json`。

## 界面

- 顶部或侧栏：站点切换/筛选（默认“全部”），旁边“添加站点”。
- 分组行：名称、站点标签、倍率、该站点余额/状态、启用按钮。
- 某个站点离线或凭据失效：该站点标红并提示重新登录，其他站点不受影响。
- 每个站点各有“去充值”（用站点的充值地址：sub2api 为 `/purchase`，new-api 取 `/api/status` 的 `top_up_link`，没有就打开站点首页）。
- 菜单栏的分组切换按站点分组。

## 添加站点流程

1. 输入站点地址（强制 HTTPS，明文 HTTP 仅允许本机地址并提示风险）。
2. 自动识别类型与版本，显示给用户确认。
3. 账号密码登录（sub2api 用邮箱，new-api 用用户名）。开启了人机验证、2FA、或关闭了密码登录的站点会在这一步提示暂不支持。
   应用不保存密码，只保存登录凭据（刷新令牌 / 刷新 Cookie）到应用数据目录的 0600 文件。
4. 校验通过后拉取分组，加入列表。


## 分组更新机制

站点的分组会不断变化，所以应用**不缓存分组列表**：

- 顶栏应用名右侧有刷新按钮和“更新于 时:分”（最近一次**真正向站点拉取**的时间，命中缓存时不变）。点按钮是手动刷新：无视缓存，重新向各站点拉取分组、余额和模型。
- 自动刷新（切回窗口、打开菜单栏面板、后台通知）遵守“一分钟内拉过就不再请求站点”：直接用缓存，只有超过一分钟才重新拉取。菜单栏面板底部也有同样的刷新按钮和时间。
- 请求的接口：`/groups/available`（sub2api）或 `/api/user/self/groups` + `/api/pricing`（new-api）。
- **后台不会刷新分组和模型。** 应用最小化或只留在菜单栏时，唯一的后台任务是“保持登录”：每 10 分钟看一眼本地时间，只有真正到了续期时间（6 小时）或站点掉线需要重连时才发请求。分组和模型只在你打开窗口/面板（一分钟内拉过就用缓存）、切回窗口、点刷新按钮、添加站点时才向站点要。
- new-api 的分组没有平台字段，无法判断该配到哪个客户端，因此在每种客户端下都展示全部非 default 分组，并在卡片上标注「该站点未对分组分类」。

请求量控制：一次打开页面只对每个站点列一次 Key（而不是每个分组一次）；窗口焦点触发的重新拉取最多每 30 秒一次；模型列表 10 分钟内不重复拉；测速逐个进行、每个分组间隔约 1 秒，且每个分组只发一次请求。

模型信息的来源，按优先级：
1. 测速或启用时用该分组的 Key 查询到的真实模型（`/v1/models`），最准；
2. sub2api 站点开了“模型广场”（`GET /api/v1/model-plaza`）时，每次拉分组都一并读取各分组的模型，**不需要 Key，也不需要测速**。带着登录令牌访问，所以你有权使用的专属分组也在里面；站点没开广场（返回 404）或读取失败，只是读不到模型，不影响分组本身；
3. new-api 的模型来自公开的 `/api/pricing`；
4. 以上都没有的分组（sub2api 没开广场），刷新时只对已经建过本应用 Key 的分组查询 `/v1/models`，不会为了拿模型去新建 Key。

## 分组成本统计（近 7 天）

口径见 `src-tauri/src/usage.rs`：**有效 Token = 输入 + 输出**，缓存读取/创建单独列出；每百万有效 Token 成本 = 实付 ÷ 有效 Token × 100 万；缓存命中率 = 缓存读取 ÷（输入 + 缓存创建 + 缓存读取）；实际倍率 = 实付 ÷ 官方价（仅 sub2api）。

- 只在用户点开某个分组的抽屉时才取数，结果在内存里缓存 10 分钟，「重新取数」可强制刷新；不做任何后台拉取。
- sub2api：`/api/v1/usage/stats`（汇总，必需）、`/usage/dashboard/models`、`/usage`（最近 100 条，取 `first_token_ms`）、`/model-plaza`（定价，换算成官方价 × 倍率）。后三者失败只在抽屉里提示缺了哪块。
- new-api：`/api/log/self?type=2&group=…`（最多 3 页共 300 条，超出时提示只统计了最近一部分），`other` 里的 `frt`、`cache_tokens`、`cache_creation_tokens`；预估价来自 `/api/pricing`（模型倍率 × 2 × 分组倍率）。new-api 没有官方价合计，没有“实际倍率”。
- 空请求基线：测速发的是一句“hi”，现在读到流结束并记录站点报告的输入 Token 数（Anthropic `message_start`、Responses `response.completed`、Chat `usage`、Gemini `usageMetadata`）；远大于几个 Token 说明站点附加了系统提示。

分组列表的「Token成本」列只显示最近一次读取到的值（浏览器本地存储 `ferrydeck.costs`，含取数时间），读取仍然是用户触发的：行内硬币图标读单个分组，标题行的硬币按钮逐个读当前列出的分组（间隔 250 毫秒，限流即停）。

成本随分组刷新一起读取（`refreshAll` → `loadAllCosts`）：手动刷新全部重读（绕过后端 10 分钟缓存），自动刷新只读缓存已过期的，逐个串行、间隔 250 毫秒，某个站点限流就跳过它剩下的分组；自动刷新静默，手动刷新才提示失败。new-api 的 `/api/pricing` 在适配器里缓存 5 分钟，批量读取时只请求一次。

## 分组列表 UI 规范

样式变量集中在 `app/src/styles.css` 顶部的 `:root`，改列宽 / 间距只改这里：

| 变量 | 值 | 用途 |
|---|---|---|
| `--col-gap` | 10px | 卡片里各列之间的间距 |
| `--col-metric` | 80px | 首字时延、倍率、Token成本、缓存命中率四个数据列的宽度（等宽） |
| `--col-models` | 96px | 模型列 |
| `--col-action` | 44px | 操作列（只放一个启用图标，紧挨模型列） |
| `--pill-h` | 22px | 药丸高度 |

规则：
- 数据列的**标题和内容都居中**，标题的中心和内容的中心对齐；分组名称列占满剩余宽度。
- 倍率、Token成本、缓存命中率、模型数量统一用药丸样式（`.rate` / `.pill` / `button.model-count`）：12px、700 字重、正文白色、浅蓝底、圆角 999px、高 22px。不要再单独给某一列设蓝色字或别的字号。
- 首字时延是纯文字（绿色为成功，红色为失败）；没有数据一律显示灰色的 `—`，正在读取显示 `读取中…`。
- 分组备注不在行里显示，鼠标放到分组名称上用快速提示（`data-tip`）显示。
- 最小窗口 1000px 宽（默认 1100px）：这个宽度下分组名称列至少还有约 170px。新增列要先算宽度，别把名称列挤没了。
- 手动刷新只重读当前列表里分组的成本；自动刷新（切回窗口、打开面板）读所有分组里过期的。成本读取同时 3 路并行，顶栏显示“读取成本 n/m”，添加站点时用提示条报进度。

## 字体、字号、字色规范

- **字体**：中文用系统自带的苹方（PingFang SC），英文数字用 SF Pro（`-apple-system`），不额外打包字体。数字一律 `tabular-nums`（等宽数字，列里的数值上下对齐）。模型名这类标识符用等宽字体（`--mono`：SF Mono / Menlo），方便逐字符辨认；成本抽屉里的模型表和模型列表的悬停提示都用它。
- **字号只有 5 档**（`--fs-*`）：11 辅助说明 / 12 列表正文与药丸 / 14 正文与标题 / 20 页面标题 / 28 大数字。不要再写别的像素值。
- **字重**：标题 600；药丸 600；应用名和大数字 700；不用 800。
- **字色**：文字用 `--accent-fg` / `--ok-fg` / `--err-fg`，填充（按钮底、提示条底、圆点）用 `--accent` / `--ok` / `--err`。浅色模式两者相同；深色模式文字色提亮（蓝 `#6b9bff`、绿 `#3fcf8e`、红 `#ff7a72`），在深色底上对比度都 ≥ 4.5。
- **灰色辅助文字分三层**：`读取中…`（稍亮）、`—` 没有数据（稍暗）、普通说明（`--muted`）。

## 我的中转站（站长：上下游一体管理）

- **身份**：登录时勾选“我是该站点管理员”，后端会实际调用一次管理接口（sub2api `GET /api/v1/admin/groups/all`，new-api `GET /api/channel/?p=1&page_size=1`）：被拒绝就不开启，站点照常作为普通站点添加。标记保存在 `sites.json` 的 `is_admin`（旧记录没有该字段，按 false）。所有管理命令都先检查这个标记。
- **读取**：sub2api = 分组 `/admin/groups/all` + 账号 `/admin/accounts`（分页，每页 200）；new-api = 渠道 `/api/channel/`（分页）+ 系统设置 `/api/option/` 里的 `GroupRatio`（倍率）、`UserUsableGroups`（备注）。读不到系统设置（非超级管理员）时只列渠道里出现过的分组名，标为不可编辑。**凭据永远不进入界面数据**：账号的 `credentials`、渠道的 `key` 在适配器里只取主机名和模型数量，其余丢弃，有测试断言返回的数据里不含密钥。
- **写入**：
  - 暂停 / 恢复：sub2api `POST /admin/accounts/{id}/schedulable`；new-api 先读完整渠道再把 `status` 改成 2 / 1 写回（只发一个字段会让站点按残缺的记录重建能力表）。
  - 移除：sub2api `DELETE /admin/accounts/{id}`；new-api `DELETE /api/channel/{id}`。
  - 编辑分组：sub2api `PUT /admin/groups/{id}`，只发改过的字段；new-api 读出 `GroupRatio` / `UserUsableGroups` 整个 JSON，改一项后 `PUT /api/option/` 写回。
- **保护**：暂停 / 移除前二次确认并列出受影响的下游（`impactOf`：没有其他运行中上游的分组标红）；移除需输入上游名称；编辑分组分两步，第二步是变更清单，倍率写明涨价 / 降价百分比；倍率在本地先校验（正数、有限）再发请求；每次写操作写一行诊断日志，不含密钥和备注内容。
- **布局**：以下游分组为主，一个下游分组一个色块（`--h` 色相循环），块里缩进的是它来源的上游账号；同一个上游服务多个分组时在每个色块里各出现一次，暂停 / 移除它对所有这些分组生效（确认框里会列出）。没有上游的分组在色块里提示，没有服务任何分组的上游放在虚线的最后一块。行里没有“启用”按钮。
- **未验证**：写入接口的字段名来自站点自己的迁移脚本和接口名，在测试里用模拟站点验证；没有在真实站点上执行过写操作。

### 我的中转站：用量、tab 与 24 小时 Token

- 窗口最小宽度 1100px、默认 1200px（站长视角比普通列表多一列）。左侧原来的“站点”改名“上游站点”。
- **用量**（`admin_usage`，10 分钟缓存，3 路并行，顶部进度）：sub2api 用管理端 `/admin/usage/stats`（可按 `group_id` / `account_id` 筛选）取 7 天汇总——分组的花费取 `total_actual_cost`（用户实付），上游账号取 `total_account_cost`（你付给上游的成本）；再翻 `/admin/usage`（最多 5 页、每页 100 条、时间倒序）取最新 50 条的首字时延，并累加 24 小时内记录的 Token 量。new-api 读管理员的全站日志 `/api/log/`（`group=` / `channel=` 筛选，最多 300 条），同样从中算出 24 小时 Token 量；记录翻满而最旧的一条还在 24 小时内时标 `≥`。
- **tab**：按分组的平台分类（new-api 没有平台字段，由渠道支持的模型推断）。tab 旁的点 = 该 tab 下“有问题”的分组数（没有来源上游 / 没有运行中的上游 / 有状态异常的上游），0 为绿点。

## 站点 tab 与左侧导航

- 左侧只有两块：「我的客户端」和（有管理员站点时）「我的中转站」。站点不再在左侧：分组列表顶部是站点 tab（`viewSiteTabs`），“全部站点”只在多于一个站点时出现；原来的站点下拉筛选取消。
- 站点 tab 上的余额和“去充值 / 移除”图标叠在同一个格子里（悬停时余额隐藏、图标出现，格子宽度取两者较大值，所以悬停不会撑宽 tab，也不会盖住站点名称）。图标平时 `pointer-events: none`，悬停后才可点，避免误点；点站点名称才是切换。
- 连不上 / 需要重新登录的站点：tab 上显示红色感叹号（外框不变红），tab 下面一条提示带“重试 / 重新登录”；选中某个站点时只显示它的提示。
- 还没有任何站点时不显示 tab，用欢迎页上的“添加站点”。

### 上游账号 ↔ 上游站点分组的关联

站点的管理接口只告诉你上游账号“有没有 API Key”，**不返回 Key 本身**（sub2api 的账号里 `credentials` 只有地址和模型映射，另有 `has_api_key`），所以没法按 Key 自动对上号。做法：地址（主机名）对应应用里已添加的上游站点时，由站长对每个上游账号选一次“它用的是我在上游站点登录的账号下的哪个分组”，保存在本机 `admin_links.json`（不含任何凭据），之后每次读上游站点那个分组**当前的**倍率。
推荐（`admin::suggest`，只是推荐，要站长确认）：账号名称末尾写了倍率（“…特价 0.09”）就在倍率相同的分组里选；有多个倍率相同的，或名称里没有倍率时，按账号名称和分组名的最长公共片段（≥3 个字符、最像的唯一一个）选；有并列就不推荐。用你的 bestapi.io 实测，9 个有对应上游站点账号的上游里 7 个有推荐，剩下 2 个是真的分不出（比如 pqh.ai 有 3 个名字几乎一样的 kiro 企业分组）。

### 在界面里创建下游分组和上游账号

`admin_create_group` / `admin_add_upstream`（`lib.rs` 的 `add_upstream`）。添加上游的流程和回滚：
1. 校验（不写任何东西）：下游分组存在；上游分组在上游站点里能用；下游和上游的类别都明确且不同则拒绝；同一个上游分组已经添加过（关联记录里有、对应账号还在）则拒绝；同名上游账号拒绝。
2. 在上游站点 `ensure_key`（建或复用 `Ferrydeck-<分组名>`）；3. 读 `/v1/models`；4. 用 Key 在上游站点发一句 “hi”（按类别选协议）——这一步通不过就**先于创建上游账号**中止，避免在站长的站点里留下一个不可用的上游；
5. 在站长的站点创建账号 / 渠道：sub2api `POST /admin/accounts`（`apikey` 类型，`credentials` = 地址 + Key + 模型映射，`group_ids`，账号倍率 = 上游分组倍率，grok 的地址带 `/v1`）；new-api `POST /api/channel/`（类型 14 / 1 / 24 / 48，创建后按名称取最新的一个 id）；
6. 默认立刻暂停（暂停失败就删掉刚建的账号）；7. 记下关联。第 4 步之后任何一步失败，如果这把 Key 是这次新建的就删掉它。
`NewUpstream` 的 `Debug` 把 Key 打码；返回给界面的 `AddedUpstream` 不含 Key。新建下游分组：sub2api `POST /admin/groups`（必须选分类，同名拒绝）；new-api 在 `GroupRatio` / `UserUsableGroups` 里加一项（需要超级管理员，同名拒绝）。
**真站验证（2026-11-09，用测试分组“测试勿用-下游”，倍率 10、备注“测试勿用”，上游账号 / 渠道先暂停）**：bestapi.io（sub2api）和 api.aicompare.club（new-api v1.0.0-rc.45）上，建下游分组 → 在 pqh.ai 建 Key 并试一次 → 创建上游账号 / 渠道 → 暂停 → 关联，整条流程都走通。过程中在 new-api 上发现 `PUT /api/channel/` 无论怎么传都返回 “Invalid parameters”（连只发 id 和 status 也一样），暂停渠道要用 `POST /api/channel/{id}/status`；这个版本的管理接口和上游 new-api 不完全一样，所以优先用专门的状态接口，404 时才退回整条写回（有测试）。第一次真跑时这个问题正好触发了“暂停失败 → 撤销刚建的渠道和 Key”的回滚，回滚也验证了。

## 左侧站点、顶部客户端（布局调整）

左侧只放两类站点，风格统一：「我的中转站」（站长）和「上游站点」（普通登录的站点，竖排的 `site-tab`，名称 + 余额，右键菜单：控制台 / 充值 / 删除；「我的中转站」卡片右键只有控制台 / 删除）。客户端（Claude Code / Claude Desktop / Codex / Gemini CLI）变成内容区顶部的 tab（`viewClientTabs`），站长视角里也显示，点其中一个就回到普通分组列表。站点异常提示（`viewSiteProblems`）在客户端 tab 下面。侧栏宽 230px。

## 分组行的“···”菜单

- `set_group_clients`：手动设置某个分组支持哪些客户端，保存在本机 `group_clients.json`（`overrides.rs`，不含凭据）。`to_view` 生成分组列表时套用，`enable_group` 用 `service::enable_with` 按手动列表校验，不再按平台判断。恢复默认 = 传空列表。
- `say_hi`：和测速同一套（`ensure_key` → 选模型 → 按客户端协议 `probe_with`），区别是 `max_tokens` 放宽到 80，并把模型回复的前 400 个字符返回给界面。
- `admin_create_downstream`：`NewGroup::validate` → 中转站创建下游分组 → `add_upstream`（和“给下游分组添加上游”同一条流程和回滚）。分组一旦创建就保留（应用没有删除分组的功能），之后添加上游失败会在错误里说明，可以到“我的中转站”里重试添加。
- `admin_downstreams`：对每个站长站点，用保存的“上游账号 ↔ 上游分组”关联加上站点的概览，算出每个上游分组底下挂着的下游分组（站点、分组、倍率），分组列表卡片底部显示。没有站长站点或没有关联时不请求。
- 悬停：`syncHover` 现在把鼠标下元素的**所有**悬停容器祖先都标成悬停（“···”菜单在分组行里面，两个都要亮，启用按钮才不会在移到菜单上时消失）。

### 删除下游分组、更换上游来源、重复添加

- `admin_remove_group`：sub2api `DELETE /admin/groups/{id}`；new-api 从 `GroupRatio` / `UserUsableGroups` 里去掉那一项（需要超级管理员）。绑在它上面的上游账号 / 渠道不动。
- `replace_upstream`（`admin_replace_upstream`）：先和添加上游一样在上游站点建 / 复用 Key、读模型、发一句 “hi”；通了之后 sub2api 用 `PUT /admin/accounts/{id}` 就地更新 `credentials`（和账号倍率），new-api 因为 `PUT /api/channel/` 实测不可用，改成“新建渠道（同样的下游分组）→ 保持暂停状态 → 删旧渠道”，删旧的失败就撤销新的。任何一步失败都撤销新建的 Key，旧账号 / 渠道原样保留；成功后把关联改成新的来源。
- 重复添加：`AddUpstreamOpts.allow_duplicate`。同一个上游分组已有关联时默认拒绝（错误里写明会共用同一把 Key）；界面上弹警告，勾选“我知道会共用同一把上游 Key，仍然添加”后才带 `allow_duplicate` 提交，默认名称加 “ (2)”。
- http：`normalize_url` 不再拒绝明文 http（本机地址早就允许）；输入 `http://` 时界面提示明文传输的风险。
- 站点卡片的悬停图标条悬浮在卡片上方（`bottom: calc(100% - 3px)`），不遮挡卡片里的名称和余额；它会压在上面一张卡片的下沿，所以测试里悬停 / 点击相邻卡片前要先把鼠标移开（`hoverTab`）。
